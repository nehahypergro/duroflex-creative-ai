# Studio speed fixes (21 November 2026)

Neha's developer said the live site is slow because "the api request has a lot of latency … every single click is
requesting multiple api calls and many db calls". Measured on a local copy of the Studio (real saved projects,
Duroflex, 67 projects), not on the live site (it needs a sign-in).

## What was happening

| Where | Before |
|---|---|
| Fresh page load | 231 requests, about 10 MB of JSON plus about 2 MB of scripts |
| Requests per project on load | the project, its saved edits, its design details (shown nowhere since the rationale panel was removed) |
| Status refresh (every few seconds) | the list, then every changed project one by one |
| Compression | none (the brand list is 288 KB raw, 44 KB gzipped; the product list 2.4 MB raw, 270 KB gzipped) |
| Page scripts | downloaded again on every visit (no ETag); the editor drawing library (316 KB) on every page |
| Server work, one project | about 180 file operations (58 reads, 104 checks, 16 blocking reads); the activity reader keeps only 8 projects |
| Server work, the list | about 540 file operations |
| Sign-in check (live site, `admin-server.js` + MongoDB Atlas) | 2 database lookups (session, user) before every request: about 460 per page load |
| Request tracking | re-read the whole project after every project request, though it records only downloads and two recovery actions |

## What changed

1. **Compression and page-file caching** (`lib/http-speed.js`, installed in `server.js`): JSON, scripts, styles,
   HTML and SVG of 1 KB or more are gzipped when the browser accepts it. Page files the server marks `no-cache` get
   an ETag; a browser that has the file gets 304 with no body. `no-store` API answers are never kept. Streams,
   images and downloads pass through unchanged.
2. **One request for the project list** (`runtime/project-list.js`, `GET /creative-ai/api/jobs?brandId=…&include=projects[&ids=…]`;
   `studio-data.js` `projects`): the page reads the short list (with each project's freshness), then asks in one
   request for the projects that are new or changed, with their saved edits. Unchanged projects come from memory, so
   a status refresh with nothing new is one small request. Overlapping loads share one request. Design details are
   no longer fetched for the list. A server without the route falls back to the old one-by-one path.
3. **Finished projects' views kept in server memory** (`runtime/view-cache.js`, `engine.view` → `viewFresh`): reused
   while a few file checks show nothing changed (project folder and job.json, activity folder and its file count,
   each edit version's folder and job.json). The checks read the shared files, so another server instance's changes
   are seen. Only finished, failed and partial projects are kept; a save through this server drops the entry; every
   entry is rebuilt after 10 minutes; each viewer (admin, owner, teammate) has its own entry. At most 600 entries.
4. **Request tracking** (`lib/admin/tracking.js`) reads the project only when it records something.
5. **Editor drawing library** loads the first time the layer editor opens (`editable-canvas.js` `ensureFabric`);
   pages that include it themselves (shared editor, proof pages) keep it.

## After (same local copy)

| | Before | After |
|---|---|---|
| Fresh page load | 231 requests, ~10 MB | 6 requests, ~720 KB |
| Reload with page files already in the browser | ~2 MB of scripts again | 11 KB (304s) |
| Opening a project / a design | 3 / 4 requests | 1 / 2 requests |
| Status refresh, nothing changed | list + changed projects | the 9 KB list |
| Project list, server cache warm | — | 376 ms for 67 projects (1.1 s cold) |

Tests: `tests/creative-ai/speed-20261121.test.js` (both brands; every test fails before).

## Not changed (open)

- **The two database lookups per request** (session, user) on the live site. Keeping a signed-in session in memory
  for a few seconds would remove most of them, but a disabled account or a sign-out on another server would then
  keep working for those seconds. That is a security trade-off for Neha to decide.
- **The product list** still sends whole product profiles (2.4–3.4 MB raw, ~270 KB gzipped).
- **Memory**: the local Studio was seen using 2.2–2.7 GB at rest and has crashed on startup before.
- How the live site stores its files (a shared network disk makes every file check slower) needs the developer to
  confirm.

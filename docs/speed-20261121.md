# Studio speed fixes (21 November 2026)

Neha's developer said the live site is slow because "the api request has a lot of latency … every single click is
requesting multiple api calls and many db calls". Measured on a local copy of the Studio (real saved projects,
Duroflex, 67 projects), not on the live site (it needs a sign-in).

## What was happening

| Where | Before |
|---|---|
| Fresh page load | 231 requests, about 10 MB of JSON plus about 2 MB of scripts |
| Requests per project on load | the project, its saved edits, its design details (shown nowhere since the rationale panel was removed) |
| Status refresh (every few seconds) | the list, then every changed project one by one |
| Compression | none (the brand list is 288 KB raw, 44 KB gzipped; the product list 2.4 MB raw, 270 KB gzipped) |
| Page scripts | downloaded again on every visit (no ETag); the editor drawing library (316 KB) on every page |
| Server work, one project | about 180 file operations (58 reads, 104 checks, 16 blocking reads); the activity reader keeps only 8 projects |
| Server work, the list | about 540 file operations |
| Sign-in check (live site, `admin-server.js` + MongoDB Atlas) | 2 database lookups (session, user) before every request: about 460 per page load |
| Request tracking | re-read the whole project after every project request, though it records only downloads and two recovery actions |

## What changed

1. **Compression and page-file caching** (`lib/http-speed.js`, installed in `server.js`): JSON, scripts, styles,
   HTML and SVG of 1 KB or more are gzipped when the browser accepts it. Page files the server marks `no-cache` get
   an ETag; a browser that has the file gets 304 with no body. `no-store` API answers are never kept. Streams,
   images and downloads pass through unchanged.
2. **One request for the project list** (`runtime/project-list.js`, `GET /creative-ai/api/jobs?brandId=…&include=projects[&ids=…]`;
   `studio-data.js` `projects`): the page reads the short list (with each project's freshness), then asks in one
   request for the projects that are new or changed, with their saved edits. Unchanged projects come from memory, so
   a status refresh with nothing new is one small request. Overlapping loads share one request. Design details are
   no longer fetched for the list. A server without the route falls back to the old one-by-one path.
3. **Finished projects' views kept in server memory** (`runtime/view-cache.js`, `engine.view` → `viewFresh`): reused
   while a few file checks show nothing changed (project folder and job.json, activity folder and its file count,
   each edit version's folder and job.json). The checks read the shared files, so another server instance's changes
   are seen. Only finished, failed and partial projects are kept; a save through this server drops the entry; every
   entry is rebuilt after 10 minutes; each viewer (admin, owner, teammate) has its own entry. At most 600 entries.
4. **Request tracking** (`lib/admin/tracking.js`) reads the project only when it records something.
5. **Editor drawing library** loads the first time the layer editor opens (`editable-canvas.js` `ensureFabric`);
   pages that include it themselves (shared editor, proof pages) keep it.

## After (same local copy)

| | Before | After |
|---|---|---|
| Fresh page load | 231 requests, ~10 MB | 6 requests, ~720 KB |
| Reload with page files already in the browser | ~2 MB of scripts again | 11 KB (304s) |
| Opening a project / a design | 3 / 4 requests | 1 / 2 requests |
| Status refresh, nothing changed | list + changed projects | the 9 KB list |
| Project list, server cache warm | — | 376 ms for 67 projects (1.1 s cold) |

Tests: `tests/creative-ai/speed-20261121.test.js` (both brands; every test fails before).

## Not changed (open)

- **The product list** still sends whole product profiles (2.4–3.4 MB raw, ~270 KB gzipped).
- How the live site stores its files (a shared network disk makes every file check slower) needs the developer to

## Memory (same day, fix 6)

The server held 800 MB–2 GB although only ~34 MB of data was in use at rest: big short-lived reads leave memory the
process does not give back. Measured with the `admin-server.js` startup on the local copy (no paid calls):

| | Before | After |
|---|---|---|
| Startup peak | 1,220 MB | 780 MB |
| Three open pages ask for the project list together | 1,819 MB | 871 MB |
| The same again | 1,959 MB | 746 MB |

Causes and changes:

- **The project list read every job.json at once.** 365 files, 134 MB (each project keeps its pinned brand knowledge),
  decoded together on every list call, and an open page asks every few seconds. The list routes now use small cached
  summaries (`runtime/job-summaries.js`): each project is read through the store's own read (workspace and access
  rules still apply) only when its job.json changes, eight at a time, keeping ~1 KB per project. `JobStore.list` reads
  eight projects at a time for every other caller.
- **Each product-list build re-parsed saved product pages and decoded a photo per product.** 28 products have no
  parsed fields saved, so 36.6 MB of saved pages were parsed again, and photos up to 3000×3000 decoded, six products at
  a time. Parses are now remembered by page hash and photo checks by file stamp and hash, and at most two pages or
  photos are worked on at once (`product-library.js`).

Tests: `tests/creative-ai/memory-20261121.test.js` (both brands; fails before).

## For the live site (same day; Neha: "ensure whatever we can manage from our code")

- **Sign-in check** (`lib/admin/accounts.js` `session`): every Studio request on the live site looked up the session
  and then the user in MongoDB Atlas (two round trips per request, ~460 per page load). A checked session is now kept
  for 10 seconds on the server that checked it. Sign-out and account changes made through that server take effect at
  once; on another server instance within 10 seconds. A session never outlives its own expiry.
  Test: `tests/admin/session-cache-20261121.test.js`.
- **Saved product pages are parsed once**: the parsed fields are kept by the page file's own stamp and saved in
  `<product>/catalog-page-fields.json` (derived data beside the product, never inside its saved snapshot; the profile
  is untouched; Git ignores `output/`), so a restart does not parse the pages again. A changed page is parsed again
  and still has to match the product's saved page hash.

Measured with the admin-server startup on the local copy after all changes:

| | Before today | After |
|---|---|---|
| Startup peak | 1,220 MB | 711–822 MB |
| At rest after startup | 1,220 MB | 346–420 MB |
| Three pages list projects together | 1,819–1,959 MB | 602–657 MB |

Not yet measured on the live site itself; it needs a redeploy, then the same checks there.

## The remaining three (same day; Neha: "fix the remaining three from our side too")

- **Product list for the Studio page** (`GET …/products?view=studio`, `product-library.js` `studioList`): leaves out
  the fields the page never reads (extracted fact fields, specification tables, audit, gaps, history, identity basis,
  and each photo's resolved source address and type). Duroflex: 2,370 KB → 943 KB raw, 274 KB → 166 KB sent. Other
  callers (the older interface) keep the full list; saved products are unchanged.
- **Photo checks after a restart**: each product's checked photos are kept in `<product>/catalog-photo-checks.json`
  by file stamp and saved hash, so a restart does not read or decode them again. A changed photo is checked again.
- **Status check** (`GET /creative-ai/api/jobs?brandId=…`): checks only the viewed brand's projects (a project's
  brand never changes, so the other brand's are not even looked at), and checks for the same brand and viewer that
  arrive while one is being worked out share its answer (a finished answer is never reused, so a save shows at once). The page asks for its brand only. Duroflex: 9 KB → 4 KB sent, half the file checks.

Tests: `tests/creative-ai/memory-20261121.test.js` (both brands; the new tests fail before).

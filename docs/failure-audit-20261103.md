## Step-by-step findings

### 1. Request construction contradicted the selected scope

Example: `creative-24281a99-5c51-4af4-ac33-6f5266e937ed` requested one continuity set and prohibited Option 2, then appended the autogenerated sentence “Produce two distinct options of the complete ordered asset set.” `conceptRoutes` contained only `continuity`. Strategy spent calls asking which instruction governed.

The current Studio builder already derives both the footer and routes from the same option count. That does not repair historical queue payloads. A new, narrow admission check rejects a contradictory **known Studio-generated footer** before source/model work. Replaying the saved inputs catches 30 of the 31 recorded scope conflicts before model work. It does not parse arbitrary customer prose for numbers, rewrite copy, or change historical jobs. Before resuming that batch, prepare corrected requests from the intended one-option briefs; do not blindly resume the conflicting originals.

The remaining case, packaging insert `creative-25eeb37a-04a1-49c5-9516-d6a2646303fc`, had a correct one-option brief. Its Art director instructions nevertheless demanded “BOTH continuity and exploration,” and shared placement guidance demanded two concepts/both layouts. Creative director and Copywriter instructions also carried generic two-option wording. These directives now follow the actual selected concept inventory, with continuity plus exploration remaining the default only when no selection is supplied. The one-option and two-option contract tests both pass; this changes neither the selected slot count nor brand evidence. Historical planning outputs are not rewritten.

### 2. Some available source evidence was not carried into the required contract

Two saved marketplace failures selected the exact product URL with `variant=51476984692868`. The selected variant source existed at that exact URL, but the `sku-destination` fact cited only the base product-page source. The strict destination check therefore lacked the required evidence relationship. Current `sku-research.js` already attaches the saved variant destination source; historical inputs still show the missing relationship.

The later Airboost strategy initially requested fonts despite four approved, hash-pinned Poppins files being available. The existing `strategy-production-assets.js` fix now supplies verified production-file evidence to strategy. Neither case means the brand assets themselves were unavailable.

### 3. Request failures were reported too generically

The two “counting service unavailable” failures were actually rejected URL inputs: both saved count diagnostics identify HTTP 400 / `invalid_value` / `url`. Existing current code has actionable diagnostics and a bounded pre-dispatch inline-input fallback for that specific case.

The later Airboost PMax portrait HTTP 400 is different: its saved response contains the status but no rejected parameter. Its exact cause cannot be reconstructed honestly. New transport diagnostics preserve safe parameter/code/type fields; this does not retroactively establish the old cause.

### 4. Image-only artwork received typography instructions

Both Airboost PMax source packages had zero embedded-copy fields and art direction explicitly prohibiting promotional text. The composed-artwork request builder nevertheless:

- told the model to create artwork “INCLUDING the exact campaign text”;
- replaced the art director's no-typography instruction with instructions to allocate typography space;
- appended a typography guide and an instruction to reproduce campaign wording.

This is a confirmed contradictory request construction path, plausibly contributing to the unwanted PMax lettering; it is not proof of the model's internal reason. New jobs pin `composedPromptVersion: 2`: zero-copy placements get explicit image-only instructions, retain no-typography direction and omit the typography guide. Physical product markings remain required. Six saved source-package comparisons confirm legacy prompt strings remain byte-identical. Both PMax prompts are also 1,260 characters shorter before transport compaction. This does not guarantee generated compliance or solve every oversized prompt.

That path still needs successful live output verification. The source measurement alone is not a completed recovery.

### 6. The standee logo was omitted from its removal mask

The source OCR row was **“9 DUROFLEX”**: the pictorial brand symbol was interpreted as a digit. `composed-quality.logos` required the normalized row to equal the brand name exactly, so it detected zero campaign-logo regions. All **21,600 pixels** in the subsequently identified logo rectangle were opaque in the original mask. The image editor therefore never had permission to change that region, and outside-mask restoration correctly preserved it. The later residual-logo check then stopped delivery.

New jobs pin `composedLogoDetectionVersion: 2`. The detector now accepts a single separated OCR symbol/digit before an exact brand name when confidence is sufficient and the region intersects the reserved campaign-logo area. Product/person protection remains in place; arbitrary adjacent words, multi-digit prefixes, uncertain detections and unexpected locations do not authorize removal. New repair candidates use the same bounded detector. Existing mask construction remains pinned for old requests. Actual original-image analysis and both-brand regression cases reproduce this cause and confirm the new region selection; no new cleanup image was generated during this audit.

### 7. Recovery had two additional admission/approval weaknesses

These are reproduced edge cases, not claimed causes of the original image failures:

- A candidate reviewer could return passing observations **and proposed corrections**. Recovery discarded the corrections and could mark the unchanged candidate ready. It now retains the proposed corrections and blocks promotion until that unresolved condition is handled. The previously successful live PMax repair returned an empty corrections list, so this finding does not invalidate that saved success.
- Repair planning checked money but omitted the parent's remaining image/reasoning-call limits. An exhausted call allowance could therefore consume the single repair attempt before dispatch failed. Planning now checks both call ceilings and the presence of a monetary allowance before starting. It never increases the original limits or resets attempts.

The broad regression run found another progress-projection edge case: a missing optional artifact directory caused `component-recovery.view` to throw, hiding the entire saved job/provider-waiting response. It now preserves the response, explicitly labels those component states unknown, and retains the existing handling of other I/O errors. The failing provider-waiting regression and a new missing-artifact test now pass.

### 8. Editor UI changes also affected verification

The two earlier save/reconnect suites targeted a removed Design tab, a hidden/disabled text box and an obsolete Add CTA control. Updated tests use actual canvas typing and the current Elements badge control. Conflict preservation, lost acknowledgements, local recovery and reopening pass for both brands.

A separate **real Fit-to-screen regression** was reproduced: after zooming in, the layout-guide SVG retained its previous 2,400-pixel size while the canvas returned to 600 pixels, leaving a large scrollable area. Fit also assumed fixed padding that no longer matched CSS. The canvas now measures current padding, and zoom/Fit synchronize the guide overlay immediately. Both-brand zoom/anchor/Fit verification passes. This UI defect does not explain upstream image-generation failures.

The carousel renderer test also expected obsolete “Set needs review” / “Review before sharing” wording. Its assertions now match “Set needs attention” / “Changes needed” while retaining flagged/ready distinctions and download checks.
